# 分析报告：线索卡滚动效果的两项前置调研

- 日期：2026-11-08
- 上游基线：`89e65b6`（beta 2.0.12），本站改动见 `doc/修改记录.md`
- 性质：**只做调研，未改任何代码**
- 验证方式：读代码 + 用 `toy/` 工程跑真实解析（`RplGenLog.execute()`）取时间轴数据

---

## 摘要

1. **平移**：引擎有三套互不相同的位移机制——切换效果位移（`_p`，脉动式进出）、媒体基准位置（`_c`，可挂贝塞尔关键帧路径）、`<move:>`（瞬移改基准）。**没有**"移动到新位置并停住"的通用关键帧动画，但可以用「`<move:>` 改基准 + 一节 `pass_in` 滑一格」组合出滚动效果，视觉上等价。
2. **立绘数量**：对话行是**硬上限 3**（`Am1`–`Am3`），另有 1 个常驻立绘 `AmS`。但**渲染器和导出器是数据驱动的**（遍历 `config.zorder`），所以放开限制属于"喂数据"式改动：核心约 50 行、GUI 约 40 行，主要成本在回归验证，不是架构问题。
3. **对本需求的直接影响**：三槽位本身正好 3 层，但"无缝滚动"的同一帧里会出现 4 张卡（旧的 3 号在退场 + 新的 1 号在进场），所以要么接受硬切，要么把层数扩到 4（建议直接做成可配置的 N）。
4. **"剧本 → 层级"的绑定规则**：层号只由角色框里的**位置**决定（第一个永远是 `Am1`），`zorder` 只决定绘制顺序，而且方向和框内顺序**相反**（Am1 画得最晚 = 在最上层）。想让 `zorder` 承担"层清单"职责是可行的，但"剧本指定层数"必须**在解析前预扫描**——时间轴列是 `execute()` 一开始就定死的（详见第五、六节）。
5. **50 层的真实成本在内存**：固定开 50 层列，空表就要 **304 MB**，填完 10 分钟视频约 215 MB；解析和渲染本身反而不是瓶颈。所以正确做法是"按实际层数生成列"，而不是把上限写成 50。
6. **更省的路（第七节）**：真正稀缺的是"**可复用的槽位**"，不是图层数量。把 1 个常驻立绘槽扩成 4–8 个（`AmS1`–`AmSn`，约 130 行 / 1 人日），就能实现"自由加图"，而且每张图可以独立位移和淡入淡出——完全不用碰"3 个立绘"和交叉溶解那套记账。零改动的话，`<animation>:(图A,图B,图C)` 已经把多张图合成为一张静态图（同屏张数无上限，代价是不能逐张动）。

## 一、平移 / 运动能力

### 1.1 图层的数据结构

每个图像图层 `X` 在时间轴上有 6 列：

| 列 | 含义 |
|---|---|
| `X` | 媒体名 |
| `X_t` | 帧序号（序列帧/GIF） |
| `X_a` | 透明度 0–100 |
| `X_c` | 中心位置 `(x,y)`，字符串 |
| `X_p` | 位移偏移 `(dx,dy)`，字符串 |
| `X_b` | 亮度 0–100 |

渲染时（`core/Medias.py:1835-1844`）：

```python
render_pos = center + eval(adjust)   # center = X_c，adjust = X_p
```

也就是说：**`_c` 决定"在哪"，`_p` 决定"相对那个位置再偏多少"**。两者都是逐帧的，所以动画的本质就是"让这两列在帧之间变化"。

### 1.2 三套位移机制

| 机制 | 语法 | 是否动画 | 结束后是否保持 | 谁来驱动 |
|---|---|---|---|---|
| 切换效果位移 `_p` | `<pass_in_right_300=10>` | 是，线性/公式曲线 | **否**，回到 0 | `MotionMethod.motion()` |
| 基准位置 `_c` | 媒体定义里的 `pos=` | 是（仅 `BezierCurve`） | 是 | `media.pos.use()` |
| 瞬移改基准 | `<move:媒体名>:(x,y)` | **否**，一帧到位 | 是 | 解析期直接改对象 |

#### (a) 切换效果位移 `_p`

由 `core/Motion.py::MotionMethod` 解析方法名，用 `_` 分隔的关键词组：

| 关键词 | 作用 |
|---|---|
| `replace` / `delay` / `cross` / `black` | 透明度模式（**注意：这不是位移**） |
| `static` / `pass` / `leap` / `circular` / `shake[N]` | 运动模式 |
| `up` / `down` / `left` / `right` / `DG<角度>` | 方向 |
| `major` / `minor` / `entire` / `<整数>` | 幅度（预设比例或**直接像素**） |
| `in` / `out` / `both` | 切入 / 切出 / 两者 |

`<名字=时长>` 的时长是本节的切入时长（帧）。曲线由全局 `<set:formula>` 决定（`linear`/`sincurve`/…）。

**实测**（`toy/` 工程，本节 `this_duration` 约 44 帧，取前 10 帧的 `Am1_p`）：

```
<pass_in_right_300=10>   → (-300,0) (-266,0) (-233,0) ... (-33,0) (0,0)    alpha 全程 100
<pass_left_300=10>       → ( 300,0) ( 266,0) ( 233,0) ... ( 33,0) (0,0)
```

即：`pass_in_right_300` = 从左侧 300px 处**向右滑**进到位；`in` 表示只做切入、不做切出，动作结束后偏移保持 0。**位移不会淡入淡出**（alpha 走 `replace` 模式，恒为 100），这对"卡片滑动但不变透明"正合适。

> 关键限制：**`_p` 是瞬态的**。`pass` 的中段是 `zeros`，尾段在 `cutout` 时回到 `-scale`、否则也是 0。所以**不能**靠 `_p` 让一张卡"永久移动到新槽位"。

#### (b) 基准位置 `_c`（贝塞尔路径）

媒体定义的 `pos` 可以是 `Pos` / `FreePos` / `PosGrid` / **`BezierCurve`**。`BezierCurve` 是真正的关键帧路径：

- `anchor`：各段终点；`control_left` / `control_right`：相对控制点
- `frame_point`：每段结束的帧号；`speed_formula`：每段的速度曲线
- `use(duration)` 返回 `duration` 帧的逐帧位置

**但**（`core/ScriptParser.py:1817`）：

```python
this_timeline[this_layer + '_c'] = this_am_obj.pos.use(this_duration)
```

每个小节都从曲线的**第 0 帧**重新取。所以贝塞尔路径只能在一节之内生效，**跨小节不连续**——做不了"贯穿整段对话的位移动画"。

实测 `<move:伊可头像>:(500,600)` 后 `Am1_c` 全帧为 `(500,600)`，说明基准位置确实会被解析期改动。

#### (c) `<move:媒体>`（瞬移）

`core/ScriptParser.py:2305-2339`：支持 `FreePos` 对象，以及图形类媒体（`Animation`/`Sprite`/`Bubble`/…）——直接 `media.pos = 新位置`。**没有过渡动画**，但配合 `_p` 的"从偏移处滑入"就能伪装成持续运动。

### 1.3 对线索卡：怎么真的滚起来

三张卡作为 `Am1`/`Am2`/`Am3`，各自基准位置在槽 1/2/3。滚动一次的动作是"所有卡整体向右挪一格"，这恰好是 `_p` 的能力（**本节所有立绘共享同一个 `_p`**）。利用这一点：

```rgl
# 滚动前的状态：Am1=卡A(槽1) Am2=卡B(槽2) Am3=卡C(槽3)
# 先把基准位置改到"新槽位"（瞬移，但此刻还看不见效果）
<move:卡A图>:(Slot2)
<move:卡B图>:(Slot3)
<move:卡C图>:(Slot4_屏幕外)
<move:卡D图>:(Slot1)

# 再让这一节的所有立绘，从"上一槽位"滑到"当前槽位"
[卡D,卡A,卡B]<pass_in_right_320=12>:……
```

因为 `_p` 起始值是 `-320`（从左侧一格处滑到 0），三张卡会同时从各自**旧槽位**滑到**新槽位**，动画结束时偏移归零，卡就停在基准位置上。老的 3 号卡基准被移到屏幕外，滑出去后就看不见了。

**这套组合的代价与缺口**：

- 卡的"上一位置"是隐式的，只能靠 `pass_in` 反推，不能精细编排轨迹；
- 所有卡必须同步、同幅度、同时长；
- 换图不能靠 `<table>`（见 3.2），每张卡要单独一个媒体 + 角色表一行；
- 非首要立绘默认 60% 透明度（`secondary_alpha`），做卡片要显式写 `[卡A,卡B(100),卡C(100)]` 或先 `<set:secondary_alpha>:100`。

### 1.4 做不到 / 需要扩引擎的

| 想做的 | 现状 |
|---|---|
| 跨小节的连续路径动画 | 不行，`pos.use()` 每节重置 |
| 三张卡各自不同的位移 | 不行，`_p` 一节只算一个（所有 Am 共享） |
| 旋转 / 缩放动画 | 不行，`scale` 只是 shake 的幅度参数，没有宽高缩放 |
| 位移的缓动多样性 | 只能改**全局** `<set:formula>`，没有逐效果的缓动 |

## 二、"只支持 3 个立绘"吗？

### 2.1 现状：对话行硬上限 3

`core/ScriptParser.py:812-831`：

```python
def charactor_parser(self, cr:str, i=0) -> dict:
    list_of_CR = RE_characor.findall(cr)
    if len(list_of_CR) > 3:
        raise ParserError('2muchChara', str(i+1))   # 报错信息就叫"超过3个角色"
    for k, charactor in enumerate(list_of_CR[0:3]):
```

其余图层的真实上限：

| 图层 | 数量 | 控制方式 |
|---|---|---|
| 对话立绘 `Am1`–`Am3` | **3** | 对话行的角色框 `[A,B,C]` |
| 常驻立绘 `AmS` | **1** | `<animation>` 放置行 |
| 对话气泡 `Bb` | 1 | 首要角色的气泡列 |
| 常驻气泡 `BbS` | 1 | `<bubble>` 放置行 |
| 背景 `BG1`/`BG2` | 2 | 交叉溶解需要两层 |

所以"同屏立绘图像"最多 4 个（3 + 常驻 1），但常驻那层是另一个系统，不能当第 4 个卡片槽位（位置由放置行的中心点决定，且只有一层）。

### 2.2 好消息：渲染与导出本来就是数据驱动的

| 位置 | 代码 | 是否硬编码 |
|---|---|---|
| MP4/预览渲染循环 | `OutputType.render()`：`for layer in self.config.zorder` | **不硬编码**，按前缀 `layer[0:2]` 分派 |
| PR 工程导出 | `OutputType.py:1222` `for layer in self.config.zorder + ['SE','Voice']` | **不硬编码** |
| 收尾逻辑 | `ScriptParser.py:2560` `for layer in config.zorder` | **不硬编码** |
| 图层顺序配置 | `ProjConfig.zorder`（列表，随项目保存） | 数据 |

只要时间轴里有 `Am4` 那一组列、`zorder` 里写了 `Am4`，渲染和导出**立刻就能工作**。

### 2.3 改造清单

| # | 位置 | 现状 | 需要改成 | 规模 |
|---|---|---|---|---|
| 1 | `ScriptParser.charactor_parser` | 超过 3 报错、切片 `[0:3]` | 上限由工程配置决定 | ~5 行 |
| 2 | `ScriptParser.render_arg` | 硬编码 `Am1`–`Am3` 的 18 列 | 按层数生成 | ~10 行 |
| 3 | `this_dialog_method` 的 `A1/A2/A3` | 5 处硬编码字典（交叉溶解记账用） | 按层数生成 | ~10 行 |
| 4 | 交叉溶解 `for k in range(1,4)` | 硬编码 3 | 按层数 | ~3 行 |
| 5 | `GUI_NewProject` 的 `all_layer` / zorder 预设 | 8 层固定 | 补 `Am4`… | ~10 行 |
| 6 | `GUI_PreviewCanvas` | `am_dict = {'Am1','Am2','Am3'}` + 字符串拼层名 | 按 zorder 遍历 | ~15 行 |
| 7 | `OutputType` 的标注 / 颜色标签 | 3 处硬编码 `Am1/Am2/Am3` | 按 zorder | ~10 行 |
| 8 | `GUI_Snippets` 角色框补全 | `([\w\ ]+,){0,2}` 最多 3 个 | 放宽 | ~2 行 |
| 9 | `ProjConfig` | `zorder` 已是自由列表 | 加"立绘层数"，缺省由 zorder 推导 | ~10 行 |
| 10 | 报错文案 / 文档 | "不能超过3个" | 跟随配置 | 少量 |

**兼容策略（推荐）**：不要引入新的全局配置项，直接**从 `zorder` 推导**立绘层数：

```python
self.am_layers = [l for l in config.zorder if re.fullmatch(r'Am\d+', l)]
```

旧工程 `zorder` 里只有 `Am1`–`Am3`，自动退回 3 层，行为与现在完全一致；新工程加 `Am4`/`Am5` 就自动生效。这样连存档格式都不用动。

### 2.4 工作量与风险

| 项 | 估计 |
|---|---|
| 核心解析/渲染/导出 | 半天（约 50 行，改动分散） |
| GUI（新建工程、预览、补全） | 半天（约 40 行） |
| 回归：预览 / 导出 MP4 / 导出 PR 工程 / 打开旧工程 | 半天 |
| **合计** | **1.5–2 人日**，属于"中等、可控"，不是架构级改造 |

风险点：

1. **交叉溶解的记账**：`this_dialog_method` 用 `A1/A2/A3` 记录每层透明度，扩层必须同步（`range(1,4)` 和 5 处字典）。
2. **旧工程**：只要坚持"层数由 zorder 推导"，旧工程天然不受影响。
3. **性能**：每层每帧一次 `blit`，时间轴每层多 6 列。10 分钟 30fps ≈ 18000 帧，5 层立绘仍在毫秒级，可忽略。
4. **GUI 预览**：它只做"当前小节的静态预览"，本来就不播放 `_p` 动画，所以不改也能用（只是预览里看不到滚动）。

## 三、对"线索卡滚动"的具体结论

### 3.1 需要几层？

| 方案 | 同屏最大卡数 | 观感 |
|---|---|---|
| 3 层 | 3 | 旧的 3 号卡必须**硬切消失**（或提前一节淡出），滚动会有一处断层 |
| **4 层** | 4 | 无缝：新的 1 号进场的同时，旧的 3 号退场 |
| 6 层 | 6 | 有余量做"叠卡""预告下一张"等效果 |

**结论：要做出你描述的"3 号移动消失 / 2→3 / 1→2 / 新的 1 号平移出现"，同一帧需要 4 张卡同时存在**，所以当前的 3 层上限正好卡住了这个效果。建议直接把上限做成可配置（推导自 zorder），一次改到位。

### 3.2 数据建模的两个坑

1. **槽位与角色行绑定**：`Am` 层的图像来自角色表的 `Animation` 列，而这一列是**受保护列**（`ScriptParser.py:2352`，`<table:>` 改它会报 `ModProtcCol`）。所以"同一个槽位换一张线索卡"必须**每张卡一个角色行**。
   - 每卡一行：可行，就是角色表会长；
   - 想省事：把 `Animation` 从保护名单里放出来（约 5 行），但这会让脚本有能力改角色表的关键列，需要额外校验。
2. **非首要立绘的透明度**：默认 60%（`secondary_alpha`），卡片要显式写 `[卡A,卡B(100),卡C(100)]`。

### 3.3 有没有"不改引擎"的替代

有，但都不理想：

- **预渲染整段滚动动画**：把"三卡滚动"做成一个 GIF/APNG/序列帧，当成一个 `Animation` 播（引擎支持动图与序列帧）。缺点是内容一变就要重新导图，无法脚本化组合。
- **用 `<animation>` 常驻立绘 + `<move:>` 硬切**：没有过渡，观感差。
- **接受硬切的三层方案**：省事但你要的"平移出现"会打折扣。

## 四、建议路线

> 如果目标是"自由加图"或"线索卡滚动"，请**先看第七节**——那里有比扩 `Am` 更省的路。
> 本节只适用于"确实要把**对话立绘**扩到 N"的场景（例如一屏站 5 个角色）。

1. **先做最小验证**：只在工程里加 `Am4` 一层（`render_arg` + `zorder` + `charactor_parser` 上限），确认滚动效果成立、导出无异常。
2. **验证通过后再通用化**：层数改为"从 zorder 推导"，报错文案、GUI 预设、补全一并跟随。
3. **可选增强**（按需，不要一次做完）：
   - 放开 `<table>` 对 `Animation` 列的限制，让槽位可以复用；
   - 给行内效果加"逐角色"语法（例如 `[卡A<pass=32>,卡B,卡C]`），解决"三张卡想要不同位移"的问题；
   - 让 `BezierCurve` 支持跨小节续播（给 `pos.use()` 加一个起始偏移量）。

## 五、现行"剧本 → 立绘层级"的定义

### 5.1 一条对话行变成六个列的完整链路

```
[角色1,角色2,角色3]<效果>:文本
        │
        ├─ RE_dialogue              → 角色框字符串 "角色1,角色2,角色3"
        ├─ charactor_parser         → {'0':{name,subtype,alpha}, '1':…, '2':…}
        │                             （>3 个报 2muchChara；只取前 3 个）
        └─ for chara_key in keys(): this_layer = 'Am%d' % (int(chara_key)+1)
                                    ↑ 层号 = 角色框里的位置
```

每层随后写入 6 个时间轴列（`core/ScriptParser.py:1776-1840`）：

| 列 | 来源 | 说明 |
|---|---|---|
| `Am{i}` | 角色表该行的 `Animation` 列 | 媒体名 |
| `Am{i}_t` | `Animation.get_tick(本节帧数)` | 序列帧；`Sprite` 且是首要角色、且该行有星标语音时，跟语音同步 |
| `Am{i}_a` | `MotionMethod.alpha(帧数, 初始alpha)` | 首要角色 100（或 `[角色(30)]` 指定），其余 `secondary_alpha`（默认 60） |
| `Am{i}_c` | `媒体.pos.use(本节帧数)` | `Pos`/`FreePos`/`PosGrid`/`BezierCurve` 都可以 |
| `Am{i}_p` | 本节**统一**的 `MotionMethod.motion(帧数)` | 一节只算一次，所有立绘共用 |
| `Am{i}_b` | 首要 100，其余 `secondary_brightness` | 亮度 |

渲染时（`OutputType.render()`）：`for layer in config.zorder` → 按 `layer[0:2]` 分派 →
`display(center=Am{i}_c, adjust=Am{i}_p, alpha=Am{i}_a, frame=Am{i}_t, bright=Am{i}_b)`。

### 5.2 三个必须知道的隐含约定

1. **层号只由"位置"决定**。`[A,B,C]` 的第一个永远是 `Am1`，第二个 `Am2`……
   没有任何语法能说"把这张卡放到 Am7"。想换层只能换它在框里的位置。
2. **`zorder` 只管绘制顺序，不管"谁在动"**。默认：
   `BG2,BG1,Am3,Am2,Am1,AmS,Bb,BbS` —— 从左到右依次 `blit`，**后画的盖前面的**，
   所以 `Am1` 在最上层。注意它和角色框顺序是**反的**：框里第一个（Am1）反而是最上。
3. **"首要角色" = 框里第一个**（`chara_key == '0'`）：它独占气泡、亮度 100、Sprite 语音同步；
   其余角色一律按"次要"处理（透明度 60%）。

### 5.3 对照表

| 剧本写法 | 落到时间轴 | 默认遮挡关系 |
|---|---|---|
| `[卡A,卡B,卡C]` | Am1/Am2/Am3 | Am1 最上 → Am3 最下 |
| `[卡A,卡B(100),卡C(100)]` | 同上，B/C 透明度改成 100 | 同上 |
| `<animation>:线索卡` | AmS（常驻，只有一层） | 在 Am1 之下、Bb 之上 |
| `<background>:背景` | BG2 | 最底层 |

## 六、放开到 50 层 / 由剧本指定 zorder，好做吗？

### 6.1 先厘清："用 zorder 锁定要播放动画的立绘"有三种落法

`zorder` 现在是**绘制顺序**。要让它承担"层清单"的职责，语义上有三条路：

| 方案 | 语义 | 改动量 | 评价 |
|---|---|---|---|
| **A. 项目级层清单** | `zorder` 里出现的 `Am\d+` 集合 = 存在的槽位，数量即上限，顺序即遮挡 | 小 | **推荐**；不动存档格式，旧工程自动退回 3 层 |
| **B. 剧本声明 + 预扫描** | 剧本头部写 `<set:am_layers>:Am1,…,Am20`，解析前先扫一遍原文再建列 | 中 | 可行；见 6.2 的坑 |
| **C. 逐行 zorder** | 每行 `[]` 决定遮挡顺序，播放中可以变序 | 大 | 时间轴要加一列"本帧层序"，渲染每帧要重排 |

> 注意：无论哪种方案，**"动画是否计算"并不是由 zorder 决定的**。现在每个出现在角色框里的角色都会算动画，
> zorder 不参与。所谓"用 zorder 锁定"，实际含义只能是"**zorder 声明了哪些槽位存在**，不存在的槽位就没有列、不参与计算"。

### 6.2 方案 B 为什么必须先预扫描

`execute()` 一进来就建好了固定列：

```python
self.render_arg = ['section','BG1',…,'Am1','Am1_t',…,'SE']   # 定长列表
```

之后才逐行解析剧本。而 `<set:…>` 是**逐行生效**的，等解析到声明层数的那一行时，列早就建好了。
所以要支持"剧本指定层数"，只能在解析前对原文做一次正则扫描（例如找 `^<set:am_layers>:`），
或者干脆放进工程设置（方案 A）。这是结构性约束，不是"多写几行"能绕过的。

### 6.3 改动清单（在 2.3 的 10 项基础上追加）

| # | 位置 | 追加改动 |
|---|---|---|
| 11 | `execute()` 开头的 `render_arg` | 改成 `固定列 + 按层清单生成 Am 列` |
| 12 | `(可选) 剧本预扫描` | 解析前扫 `<set:am_layers>` / `<set:zorder>` |
| 13 | GUI 新建工程 / 工程设置 | 图层清单可编辑（不是固定 8 层预设） |
| 14 | 默认 zorder 的插入位置 | `Am4`… 必须插在 `AmS` **之前**，否则卡片会盖住气泡 |

### 6.4 规模与性能（实测数据）

用与 `render_arg` 同构的 DataFrame 实测（10 分钟视频 = 18000 帧 @30fps）：

| 立绘层数 | 时间轴列数 | 空表（30000 行预分配） | 填充 18000 帧后 |
|---|---|---|---|
| 3 | 50 | 45.8 MB | 29.4 MB |
| 10 | 92 | 84.2 MB | 57.1 MB |
| **50** | **332** | **304.0 MB** | **215.0 MB** |

PR 工程导出（`parse_timeline_anime` 对每层做一次 `iterrows` 遍历全部帧）：

| 层数 | 耗时 |
|---|---|
| 3 | 0.64 s |
| 50 | ≈ 10.7 s（外推） |

结论：

- **解析与渲染都不是瓶颈**：`NA` 层在渲染循环里只做一次字符串比较就 `continue`，成本可忽略；
  解析时每层也就多几次列赋值。
- **内存是主要成本**：固定开 50 层列，每个工程都要吃 ~300 MB（空表预分配就已经 304 MB）。
  所以**不要写死 50**，要按"实际声明的层数"生成列——用 3 层就只开 3 层的列。
- **PR 导出会变慢但可接受**（+10 秒量级）；顺手把 `iterrows` 换成向量化还能再快一个数量级。
- **真正的渲染瓶颈只在"50 层同时有内容"时**：每帧 50 次全屏级 `blit`，1080p 下大概率掉到 20fps 以下。
  实际做线索卡时同屏最多 4–6 张，不会触发。

### 6.5 结论

| 问题 | 回答 |
|---|---|
| 完全放开上限难吗？ | **不难**。没有一处算法依赖"3"这个数字，只是被写死在十几个地方；核心约 50 行、GUI 约 40 行 |
| 放开到 50 有意义吗？ | **不建议真开 50 列**。按需生成（3–8 层）内存最优；50 层能吃 300 MB，且几乎用不到 |
| 由剧本指定 zorder 可行吗？ | **可行但要预扫描**（见 6.2）。如果只是"指定层数"，放工程设置更省事 |
| 用 zorder 锁定动画对象？ | 语义上只能做到"声明槽位集合"；真正的"每层独立动画"是另一个特性（见 1.4） |

### 6.6 建议的最小实现路径

1. **层清单只有一个来源**：`am_layers = [l for l in zorder if re.fullmatch(r'Am\d+', l)]`，排序后即槽位顺序；
2. `render_arg` 按 `am_layers` 生成（不再写死 3 层）；
3. `charactor_parser` 的上限 = `len(am_layers)`，报错文案跟着变；
4. `this_dialog_method` 的 `A1/A2/A3` 改成 `{f'A{i}':0 for i in …}`，交叉溶解的 `range(1,4)` 改成 `range(1, N+1)`；
5. `GUI_NewProject` 的 `all_layer` / zorder 预设由清单生成；
6. 先跑通 4 层（线索卡的最小需求），确认观感后再考虑要不要加剧本声明。

## 七、"自由加图"的更省方案

前面二、六节都在讨论"把立绘层数从 3 加到 N"。但如果目标只是**"画面上想放几张图就放几张"**，
那不是最优解。这一节换一个切法。

### 7.1 先换成本模型：要的是"槽位"，不是"图层数"

时间轴的成本模型是**每层一列组**（6 列），加一层就多 6 列 × 每帧一次遍历。所以"50 层"贵。

但真正需要的是**同屏可见的图片数**，不是"图片总数"——卡片会走，槽位可以复用。
做线索卡滚动，同屏最多 4–6 张；做普通场景，2–4 张。**争的从来不是 50 层，而是 4–8 个可复用的槽位。**

### 7.2 现有能力盘点（零改动就能用的）

| 手段 | 同屏张数 | 关键限制 |
|---|---|---|
| 对话立绘 `Am1`–`Am3` | 3 | 需要角色表行；所有层**共享**位移；非首要默认 60% 透明 |
| 常驻立绘 `AmS` | 1 | 单层，但支持动图/序列帧，可 `<move:>`、可逐段换效果 |
| `<animation>:(A,B,C…)` → `GroupedAnimation` | **任意多** | 见下，是个"合成为一张静止图"的手段 |
| 背景 `BG2` | 1 | 在最底层 |
| 气泡 `Bb`/`BbS` | 2 | 是排版文字，不是自由图 |

**`GroupedAnimation` 值得单独说**（`Medias.py:1963`）：`<animation>:(图A,图B,图C)` 会在解析期把这三张
**合成为一张全屏静止图**，之后整体只有一次 `blit`。

- ✅ 同屏张数无上限、渲染成本只有 1 次
- ❌ 子对象必须是**单帧**（`length > 1` 直接报 `DA2GA`，动图/序列帧不行）
- ❌ 合成后是"一张图"，三张卡不能再各自移动、各自淡出
- ❌ 每组占一张 1920×1080 的 RGBA 画布 ≈ **8 MB**，滚动 20 步就是 20 个组 ≈ 160 MB
- ❌ 组的位置固定为 `(0,0)`，整体只能一起平移

所以它适合"一次性摆好的一排静态图"，不适合需要逐张控制动画的场景。

### 7.3 推荐方案：把"常驻立绘"从 1 个扩展成 N 个槽位（`AmS1`–`AmSn`）

动机很直接：**你已经有一个"任意图像、任意位置、可独立设置效果"的机制了，只是只有一个。**

```rgl
# 现状：只有一个常驻立绘槽
<animation>:图A

# 建议：编号槽位，各自独立
<animation:1>:图A
<animation:2>:图B
<animation:3>:图C
<animation:4>:NA        # 清空 4 号槽
```

为什么这比"把 Am 扩到 N"更好：

| 维度 | 扩 `Am` 到 N | 扩 `AmS` 到 N |
|---|---|---|
| 要不要角色表行 | **要**（每张卡一行，且 `Animation` 列是受保护列） | **不要**，直接写媒体名 |
| 是否碰交叉溶解记账（`A1/A2/A3`，最脏的部分） | 要 | **不碰** |
| 每张图能否独立位移/淡入淡出 | 不能（`_p` 一节共享一个） | **能**（每个槽位有自己的 `<animation:N>` 行和效果） |
| 与气泡、语音、首要角色耦合 | 有 | 无 |
| 槽位数 | 得开到很大才够用 | 4–8 就够（同屏张数） |

**关键收益**：`place_anime_execute` 本来就是"给一个槽位设置内容 + 中心 + 效果，并填充到下一次设置之前"，
这正是"一个图像精灵"的语义。把它从单例改成字典，就一步到位了。

改动清单：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `render_arg` | `AmS` → `AmS1..AmSn`（`n` 来自配置，默认 4） |
| 2 | `place_anime_execute` / `this_placed_animation` | 单例元组 → `{槽号: 元组}` |
| 3 | `<animation>` 解析行 | 支持可选的 `:槽号`，如 `<animation:2>:`；不写则默认 1（兼容旧剧本） |
| 4 | `zorder` | 插入 `AmS2`…，位置必须在 `Bb` **之前** |
| 5 | `parse_timeline_anime` | `layer[-1] != 'S'` 的判断要改成 `not layer.startswith('AmS')`（否则 `AmS2` 会被当成非持久层切 clip） |
| 6 | GUI 图层清单 | 与第 4 项同步 |

**估算：约 120–150 行，1 人日左右**，风险明显低于扩 Am（不碰角色表、不碰交叉溶解）。

### 7.4 备选：新开一个通用图像层 `Im1..ImN`

语义上更干净（"这就是一张图，不是立绘"），但要新增渲染分派分支（现在只认 `BG`/`Am`/`Bb` 前缀）、
导出兼容（`parse_timeline_anime` 里的前缀判断）、GUI 图层面板。
**多改 5–6 处，收益主要是命名清晰**——除非你打算长期把它当核心功能，否则复用 `AmS` 更划算。

### 7.5 三条路线的对比

| 路线 | 改动量 | 同屏上限 | 逐张独立动画 | 需要角色表 | 内存成本 | 主要风险 |
|---|---|---|---|---|---|---|
| A. 扩 `Am` 到 N（第二/六节） | ~90 行 | N | ❌ 共享位移 | ✅ 需要 | 50 层 ≈ 300 MB | 交叉溶解记账、旧工程 |
| **B. 扩 `AmS` 到 N（推荐）** | ~130 行 | N（默认 4–8） | ✅ 独立 | ❌ 不需要 | 8 层 ≈ 40 MB | 槽位语义、导出前缀判断 |
| C. 用 `GroupedAnimation`（零改动） | 0 | 任意 | ❌ 合成成一张 | ❌ | 每组 8 MB | 只能是单帧；不能逐张动 |

### 7.6 结论

1. **如果只是"想多放几张图"**：走 B，4–6 个槽位就够，完全不用碰"3 个立绘"这道墙。
2. **如果要做线索卡滚动**：B 更好——每个槽位有自己的效果和中心，滚动可以逐张精确编排
   （`<move:图>:(新槽位)` 改基准 + `<animation:N>` 的 `pass_in_<方向>_<槽宽>` 滑一格），
   而且不需要"4 张卡同屏"以外的任何扩容。
3. **如果只是静态摆一排图**：先用 C 试，一条 `<animation>:(图A,图B,图C)` 就能看到效果，零改动。
4. 只有在"真的需要同屏十几张、且每张要独立动画"时，才值得回到 A（扩 Am）。

> 换句话说：**瓶颈不是"图的数量"，而是"可复用槽位的数量"。把 1 个常驻立绘槽变成 4–8 个，比把 3 个对话立绘变成 50 个便宜得多，也更贴合需求。**

**实现状态**：方案 B 已落地（`200d1a3`），常驻立绘扩成 `AmS1`–`AmS6` 六个槽位，
语法为 `<animation:N>:对象`（N 省略等于 1，旧剧本/旧工程自动兼容）。
可直接开发的剧本样例见 `doc/用例-线索卡槽滚动.md`。
